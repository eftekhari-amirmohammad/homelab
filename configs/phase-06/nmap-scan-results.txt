-------------------------------------------------------------------------------
[3] CONTROLLED EXPERIMENT - ICMP RATE LIMITING
-------------------------------------------------------------------------------
Observation to explain: in scan [2], 988 ports gave no response while only 10
returned an ICMP admin-prohibited message - although all 998 are treated
identically by the firewall.

Hypothesis: the Linux kernel rate-limits outgoing ICMP error messages.

Evidence from the target (LAB-WEB01):

$ sysctl net.ipv4.icmp_ratelimit net.ipv4.icmp_ratemask
net.ipv4.icmp_ratelimit = 1000        # minimum 1000 ms between ICMP errors
net.ipv4.icmp_ratemask  = 6168        # bits 3,4,11,12 - bit 3 = ICMP type 3

Verification by deliberate reproduction - one packet per second:

$ sudo nmap -sS -p 8000-8004 --scan-delay 1s --reason 192.168.100.20

All five ports: filtered / admin-prohibited / ttl 64 / received arp-response

Result: with a one-second delay, 5 of 5 ports answered instead of a small
        fraction. The rate limit - not the firewall configuration - explains
        the two different port states.

Independent quantitative confirmation from scan [4]:
        135.50 seconds of scanning produced 128 ICMP replies
        = approximately 1 reply per second = the configured 1000 ms limit.

[8] DEFENDER'S VIEW - WHAT THE TARGET RECORDED
-------------------------------------------------------------------------------
$ sudo grep "Nmap" /var/log/nginx/access.log | tail -3

192.168.100.50 - - [03/Aug/2026:15:14:45 +0330] "POST /sdk HTTP/1.1" 404 3971 "-" "Mozilla/5.0 (compatible; Nmap Scripting Engine; https://nmap.org/book/nse.html)" "-"
192.168.100.50 - - [03/Aug/2026:15:14:45 +0330] "GET /HNAP1 HTTP/1.1" 404 3971 "-" "Mozilla/5.0 (compatible; Nmap Scripting Engine; https://nmap.org/book/nse.html)" "-"
192.168.100.50 - - [03/Aug/2026:15:14:45 +0330] "GET /evox/about HTTP/1.1" 404 3971 "-" "Mozilla/5.0 (compatible; Nmap Scripting Engine; https://nmap.org/book/nse.html)" "-"

Observations:
  - The scanner identifies itself in the User-Agent header. This is correct
    behaviour for an authorised scan, but a real attacker can forge that field.
  - The requested paths reveal the intent: /sdk probes for a VMware vSphere
    management interface, /HNAP1 for a router administration interface,
    /evox/about for embedded devices. A normal visitor never requests these.
  - Detection therefore has to rely on behaviour patterns, not on self-declared
    identifiers: several 404 responses on unusual paths within one second.
  - The scanning host also disclosed its own tooling: "curl/8.14.1".
  - The +0330 timestamps in these lines predate the timezone correction below.


-------------------------------------------------------------------------------
[9] FINDING DISCOVERED DURING THE AUDIT - INCONSISTENT TIME ZONES
-------------------------------------------------------------------------------
The nginx log wrote "15:14:45 +0330" while nmap reported "11:46 UTC" for the
same moment. The clocks were synchronised, but the machines displayed time in
different zones.

$ timedatectl | head -4        # LAB-WEB01, before
               Local time: Mon 2026-08-03 15:23:50 +0330
           Universal time: Mon 2026-08-03 11:53:50 UTC
                 RTC time: Mon 2026-08-03 11:53:50
                Time zone: Asia/Tehran (+0330, +0330)

LAB-DC01 and LAB-SEC01 were already running in UTC; only LAB-WEB01 differed.

Why this matters: during incident analysis the logs of several machines have to
be correlated. Different time zones make the order of events ambiguous and every
manual conversion is a chance to make a mistake.

Remediation:

$ sudo timedatectl set-timezone UTC
$ timedatectl | head -4        # after
               Local time: Mon 2026-08-03 11:55:09 UTC
           Universal time: Mon 2026-08-03 11:55:09 UTC
                 RTC time: Mon 2026-08-03 11:55:09
                Time zone: UTC (UTC, +0000)

Verification at the place where it actually matters - the log file itself.
The first check after the change still showed the old zone:

192.168.100.50 - - [03/Aug/2026:15:26:08 +0330] "HEAD / HTTP/1.1" 200 0 "-" "curl/8.14.1" "-"

After reloading nginx, new worker processes read /etc/localtime again:

192.168.100.50 - - [03/Aug/2026:11:57:17 +0000] "HEAD / HTTP/1.1" 200 0 "-" "curl/8.14.1" "-"

Result: system time zone and log time zone are both UTC.
        Checking timedatectl alone would have reported the finding as fixed
        while the log file was still wrong.
